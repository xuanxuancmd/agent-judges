12. **[major]** (置信度: 0.80)

   - 依据: FR-2 要求为 6 种语言实现跨文件调用/导入/继承解析，spec 仅说'解析应基于语言感知的规则，不使用LLM'。NFR-6 提供部分降级（'未能解析的调用应标注为 AMBIGUOUS'），但未提供：(1) 各语言导入系统复杂度评估；(2) 解析准确率目标；(3) 动态导入处理方案；(4) 部分解析失败对 FR-3/FR-5 的级联影响评估。跨文件解析是本规格技术风险最高的部分——GitNexus 为此独立设置 Resolution 流水线阶段并实现了接收者类型推断。
   - 建议: 增加技术风险章节，按语言评估解析复杂度，定义解析准确率目标，明确动态导入等无法静态解析的场景标注为 AMBIGUOUS 并说明对 FR-3/FR-5 下游能力的降级影响。

13. **[major]** (置信度: 0.80)

   - 依据: FR-2 说明'跨文件引用解析在增量更新场景下可能产生短暂的悬空边'。FR-5 影响映射'沿CALLS/HERITAGE边传播影响，返回受影响的执行流列表'。当 CALLS/HERITAGE 边指向已变更但未重新提取的符号时，影响分析结果将不完整或错误。spec 未定义 FR-5 遇到悬空边时的行为——是跳过、报错、还是标注为 STALE。
   - 建议: 定义 FR-5 遇到悬空边时的行为：标注为 STALE_IMPACT 并在结果中单独报告，或要求先执行 --update 完成重新提取后再运行影响分析。

15. **[major]** (置信度: 0.82)
   - 问题: FR-3 执行流追踪未处理动态分发，FR-2 缺少接收者类型推断，OO 代码调用链将不完整
   - 依据: FR-3 沿 CALLS 边构建调用链，FR-2 定义 CALLS 边为'函数/方法调用→被调用函数/方法'。但面向对象代码中方法调用通过接口/虚函数分发，CALLS 边只能指向接口方法声明而非具体实现。GitNexus 在 Resolution 阶段明确实现了'构造器类型推断'和'self/this接收者类型推断'（3.1 节）。spec 的 FR-2 未包含接收者类型推断，导致 FR-3 对 OO 代码的执行流追踪将不完整——调用链在接口方法处断裂。
   - 建议: 在 FR-2 增加接收者类型推断能力，或显式记录为 FR-3 的已知限制并描述动态分发场景下 CALLS 边的解析策略。

16. **[major]** (置信度: 0.85)

   - 依据: FR-3 执行流追踪'沿 CALLS 边从入口点出发，构建有向调用子图'，但未定义循环依赖终止条件或最大追踪深度。FR-4 影响分析'按调用深度分层'但未定义最大深度或 budget 限制。FR-5 git-diff 影响映射'沿 CALLS/HERITAGE 边传播影响'但未定义传播终止条件。对于存在循环调用（A→B→A）的代码库——这在真实代码中极为常见——无终止条件的图遍历将产生无限循环或无限增长的 process 节点。
   - 建议: 为 FR-3/FR-4/FR-5 定义最大深度/budget 参数、循环检测机制（visited set 或 SCC 折叠），以及超限时的截断行为与输出标记。

18. **[major]** (置信度: 0.87)

19. **[major]** (置信度: 0.90)
   - 问题: 调用链（FR-3）与影响分析（FR-4）缺少循环检测与深度限制设计，将导致无限循环或栈溢出
   - 依据: FR-3 执行流追踪'沿CALLS边从入口点出发，构建有向调用子图'，FR-4 影响分析'按调用深度分层'。两者均涉及图遍历但未提及：(1) 循环调用（递归函数、互递归、A→B→A）的检测与处理；(2) 最大遍历深度限制；(3) 超大调用链的性能保护。实际代码中递归和互递归极为常见，无循环检测的图遍历将导致无限循环或栈溢出。此发现获 spec-reviewer agree-and-amplify，确认为会导致实现阶段实际故障的硬性设计缺陷。
   - 建议: 在 FR-3 和 FR-4 增加循环检测（访问标记或 Tarjan 算法识别强连通分量 SCC）和最大深度参数（可配置，默认值如 10），循环边标注为 RECURSIVE。
