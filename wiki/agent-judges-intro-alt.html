摘要 Abstract

agent-judges 是一套 AI 产出物审计系统:由确定性引擎驱动多名互相挑战的 reviewer,对需求文档、规格、设计、测试计划乃至外部检视报告等一切 AI 产出进行 四阶段对抗辩论,并输出带量化置信度、可人工升级的裁决。

立项前提为:单 agent 审查不可靠——幻觉、遗漏、过度自信是其结构性缺陷。 系统的全部设计,均由这一前推导出。

关键词:对抗审查 · 确定性编排 · 渐进门控 · 主动验证 · 元审查校准 · 置信度升级

第一条

立场

设计立场共六款,为本系统全部技术决策的推导起点。

1.1

单 agent 审查,不应被直接信任。

单一 reviewer(无论多强的模型)存在幻觉、遗漏与过度自信,这是结构性缺陷。凡 AI 产出物,均应经多 reviewer 对抗审查。

1.2

对抗性由结构提供,而非由单兵能力提供。

固定四阶段流程(独立评审 → 对抗辩论 → 盲评终判 → 裁决合成)逼 reviewer 互相挑战。reviewer 无自主性、不调工具、不控制流程——是合议庭,不是 agent team。

1.3

流程编排权属于确定性引擎。

门控、辩论、合成、升级由 prepare / resume 状态机推进;任何 LLM(含宿主)不得编排流程——单 agent 不可靠是立项前提,故编排权不可交给单个 LLM。

1.4

审查者亦不可靠,审查结果应可被审查。

verdict 可作为输入,交由 ≥2 个异构 meta-reviewer 复审;置信度经显式公式校准(见 2.4),升级判定只认校准值。

1.5

高置信自主,低置信交人。

每条 finding 与整体裁决均携带量化置信度;校准值低于阈值,自动标记 escalate_to_human。系统目标不是替代人,而是把人力只用在判不动的地方。

1.6

审查对象是产出物,不是执行轨迹。

覆盖软件开发全管线交付物:需求、规格、设计、实现对照、测试计划、部署配置、文档、外部检视报告。不含代码风格等传统 code review 范畴(见第四条)。

第二条

流程

零参数调用时的完整程序:两道纯规则门 + 图谱证据收集 + 四阶段辩论 + 可选元审查。

2.1 端到端流程 · 两道门 × 四阶段

两道门均为纯规则门,零 LLM 预分类:G1 决定早停;G2 依据 Phase 1 实测信号(severity / 置信 / 共识)决定续跑强度——standard(1 轮辩论)或 thorough(2 轮辩论 + 元审查)。哨兵结论保留计入面板;完整路径记录于 verdict 的 route 字段,可复盘。

2.2 主动验证 · 图谱证据收集(审查代码类产出时)

环节程序
收集 引擎在调用 reviewer 前,自动从本地 graphify 代码知识图谱提取结构证据——调用链、依赖关系、跨文件引用——注入 reviewer prompt 的 context
验证 reviewer 仍为纯 LLM,但每条 finding 可对照代码实际结构验证:"需求遗漏了 X"的判断有事实依据,而非仅凭模型记忆
边界 以预构建图谱替代 AaaJ 的 tree-sitter / BM25 / embedding 工具层,无需自建;图谱不存在时静默降级为纯 LLM 模式,不阻断主流程

2.3 强度档位

档位Reviewer辩论轮元审查LLM 调用适用
fast10—1短文快检 · CI 门禁 · 迭代内自检
standard21—~6常规文档审查
thorough32✓~15关键交付物 · 终审

2.4 元审查与置信度校准

thorough 档下,verdict 交由 ≥2 个异构 meta-reviewer 复审,审查维度:漏判、过判、置信度失准、 推理缺口、共识假象、完整性。校准用显式公式,升级判定只认校准值:

calibrated = confidence × ( 1 − meta_penalty )  // critical 0.5 · major 0.3 · minor 0.1
escalate_to_human → 人工裁决

2.5 记录样本 · 机器可读输出(节选)

Evidence // verdict.json
"verdict": {
  "severity": "major",
  "confidence": 0.65,
  "calibrated_confidence": 0.455,
  "escalate_to_human": true,
  "findings": [ { 证据引用 · 建议 · 逐条置信度 } ]
}
第三条

技术要点

支撑上述流程的八项已实现能力。

异构 reviewer 面板HETEROGENEOUS PANEL

不同角色配不同模型(如 Claude + GPT-4o),避免同模型共享盲区;模型写在 reviewer 模板 frontmatter,省略即用宿主默认模型。

多数投票MAJORITY VOTE

同一 reviewer 可配置多次调用后投票聚合,作轻量级反幻觉(继承 Agent-as-a-Judge 原始算法)。

元审查校准META-REVIEW

审查结果再被审查:≥2 个 meta-reviewer 异构复审,置信度按显式公式校准而非覆盖(见 2.4)。

置信度升级路由ESCALATION

校准置信低于阈值 → escalate_to_human;finding 附证据引用与可执行建议,交人即可裁决。

零代码扩展EXTENSIBLE

reviewer 用 Markdown 模板定义(persona + checklist),SKILL.md 知识包注入领域 rubric;新增视角不改代码。

宿主零配置ZERO-CONFIG HOST

一条命令装入 Claude Code / OpenCode:judge-manager 与实体 reviewer Agent 的模型、凭证、额度全部来自宿主;不依赖任何 headless CLI。

递归自审RECURSIVE

verdict 序列化后可再次作为输入被审查,深度上限 2——"审查者不可靠"的主张对系统自身同样成立。

主动验证 · 图谱证据ACTIVE VERIFICATION

reviewer 不调工具,但引擎为其预先收集代码结构证据,使每条 finding 可对照代码实际结构验证(见 2.2);以预构建图谱替代 AaaJ 工具层,无需自建。

第四条

边界与渊源

4.1

不做传统 code review。

代码风格、命名规范、设计模式、性能微优化不属本系统职责,由 SonarQube / ESLint / 人工处理。

4.2

可审查检视工具的产物。

外部代码检视报告本身是否可靠(覆盖度、误报漏报、定级合理性、建议可执行性)可作为输入被本系统复审。

4.3

渊源。

受 Agent-as-a-Judge(ICML 2025)启发的重写:继承其多数投票聚合、置信度公式与 AUROC 校准评估;辩论编排、元审查、升级路由与状态机为全新构建。MIT 许可。
