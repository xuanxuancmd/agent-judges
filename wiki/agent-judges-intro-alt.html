摘要 Abstract

agent-judges 是一套 AI 产出物审计系统:由确定性引擎驱动多名互相挑战的 reviewer,对规格文档、设计文档、实现代码、测试代码、部署配置、API 文档乃至外部检视报告等一切 AI 产出进行 四阶段对抗辩论,并输出带量化置信度、三级行动决策(green/yellow/red)、可人工升级的裁决。

立项前提为:单 agent 审查不可靠——幻觉、遗漏、过度自信是其结构性缺陷。 系统的全部设计,均由这一前推导出。

关键词:对抗审查 · 确定性编排 · 渐进门控 · 溯源标记 · 推理策略多样性 · 自动辩论强度 · 元审查校准 · 三级行动决策

第一条

立场

设计立场共六款,为本系统全部技术决策的推导起点。

1.1

单 agent 审查,不应被直接信任。

单一 reviewer(无论多强的模型)存在幻觉、遗漏与过度自信,这是结构性缺陷。凡 AI 产出物,均应经多 reviewer 对抗审查。

1.2

对抗性由结构提供,而非由单兵能力提供。

固定四阶段流程(独立评审 → 对抗辩论 → 盲评终判 → 裁决合成)逼 reviewer 互相挑战。reviewer 无自主性、不调工具、不控制流程——是合议庭,不是 agent team。

1.3

流程编排权属于确定性引擎。

门控、辩论、合成、升级由 prepare / resume 状态机推进;任何 LLM(含宿主)不得编排流程——单 agent 不可靠是立项前提,故编排权不可交给单个 LLM。

1.4

审查者亦不可靠,审查结果应可被审查。

verdict 可作为输入,交由 ≥2 个异构 meta-reviewer 复审;置信度经显式公式校准(见 2.4),升级判定只认校准值。

1.5

高置信自主,低置信交人。

每条 finding 与整体裁决均携带量化置信度;系统输出三级行动决策——green(AI 可自行修复)、yellow(需人工确认方案)、red(必须人工介入)。系统目标不是替代人,而是把人力只用在判不动的地方。

1.6

审查对象是产出物,不是执行轨迹。

覆盖软件开发全管线交付物:规格文档、设计文档、实现对照、单元测试、集成测试、部署配置、文档、测试计划、外部检视报告。需求收集(原始输入)不在审查范围;需求澄清/分解/优先级等过程活动的产出合入规格文档,由 spec-reviewer 统一覆盖。不含代码风格等传统 code review 范畴(见第五条)。

第二条

流程

零参数调用时的完整程序:两道纯规则门 + 图谱证据收集 + 四阶段辩论(含溯源标记与自动辩论强度) + 可选元审查 + 三级行动决策。

2.1 端到端流程 · 两道门 × 四阶段 × 三级决策

两道门均为纯规则门,零 LLM 预分类:G1 决定早停;G2 依据 Phase 1 实测信号(severity / 置信 / 共识)决定续跑强度——standard(1 轮辩论)或 thorough(2 轮辩论 + 元审查)。哨兵结论保留计入面板;完整路径记录于 verdict 的 route 字段,可复盘。

Phase 2 辩论中,reviewer 引用他人主张须标注溯源标记([✓已确认] / [✗已反驳] / [?未验证]),不带标记的引用视为无效反驳。质疑强度由 Phase 1 信号自动推断——critical 或分歧大 → 高质疑(0.9);全员一致且 minor → 低质疑(0.4)快速收敛。

2.2 审查范围与场景路由

场景产出物reviewer 来源
document 规格文档、设计文档、测试计划、API 文档/README spec-reviewer · design-reviewer · test-plan-reviewer · documentation-reviewer
code 实现代码、单元测试、集成测试、部署配置(Dockerfile/IaC) implementation-vs-requirement · unit-test · integration-test · deployment-config · dangerous-operation-scanner
review-report 外部代码检视报告(SonarQube/ESLint/人工 review) external-code-review-auditor · deception-detector

需求收集(原始输入)不在审查范围;需求澄清/分解/优先级等过程活动的产出合入规格文档,由 spec-reviewer 统一覆盖。用户传入不同文件时,引擎按 --scene 路由到匹配的 reviewer 模板。

2.3 主动验证 · 图谱证据收集(审查代码类产出时)

环节程序
收集 引擎在调用 reviewer 前,自动从本地 graphify 代码知识图谱提取结构证据——调用链、依赖关系、跨文件引用——注入 reviewer prompt 的 context
验证 reviewer 仍为纯 LLM,但每条 finding 可对照代码实际结构验证:"需求遗漏了 X"的判断有事实依据,而非仅凭模型记忆
边界 以预构建图谱替代 AaaJ 的 tree-sitter / BM25 / embedding 工具层,无需自建;图谱不存在时静默降级为纯 LLM 模式,不阻断主流程

2.4 强度档位

档位Reviewer辩论轮元审查LLM 调用适用
fast10—1短文快检 · CI 门禁 · 迭代内自检
standard21—~6常规文档审查
thorough32✓~15关键交付物 · 终审

2.5 元审查与置信度校准

thorough 档下,verdict 交由 ≥2 个异构 meta-reviewer 复审,审查维度:漏判、过判、置信度失准、 推理缺口、共识假象、完整性。校准用显式公式,升级判定只认校准值:

calibrated = confidence × ( 1 − meta_penalty )  // critical 0.5 · major 0.3 · minor 0.1
校准后判定 → 3 级行动

第三条

技术要点

支撑上述流程的十二项已实现能力。前八项为原有能力,后四项为本轮新增。

异构 reviewer 面板HETEROGENEOUS PANEL

不同角色配不同模型(如 Claude + GPT-4o),避免同模型共享盲区;模型写在 reviewer 模板 frontmatter,省略即用宿主默认模型。

多数投票MAJORITY VOTE

同一 reviewer 可配置多次调用后投票聚合,作轻量级反幻觉(继承 Agent-as-a-Judge 原始算法)。

元审查校准META-REVIEW

审查结果再被审查:≥2 个 meta-reviewer 异构复审,置信度按显式公式校准而非覆盖(见 2.5)。

置信度升级路由ESCALATION

校准置信低于阈值 → 三级行动决策(red/yellow/green);finding 附证据引用与可执行建议,交人即可裁决。

零代码扩展EXTENSIBLE

reviewer 用 Markdown 模板定义(persona + checklist + reasoning_strategy),SKILL.md 知识包注入领域 rubric;新增视角不改代码。

宿主零配置ZERO-CONFIG HOST

一条命令装入 Claude Code / OpenCode:judge-manager 与实体 reviewer Agent 的模型、凭证、额度全部来自宿主;不依赖任何 headless CLI。

递归自审RECURSIVE

verdict 序列化后可再次作为输入被审查,深度上限 2——"审查者不可靠"的主张对系统自身同样成立。

主动验证 · 图谱证据ACTIVE VERIFICATION

reviewer 不调工具,但引擎为其预先收集代码结构证据,使每条 finding 可对照代码实际结构验证(见 2.3);以预构建图谱替代 AaaJ 工具层,无需自建。

辩论溯源标记PROVENANCE TAGGINGNEW

Phase 2 辩论中,reviewer 引用他人主张须标注三态认知状态:[✓已确认](在被审查内容中验证)、[✗已反驳](发现不成立)、[?未验证](无法确认)。不带标记的引用视为无效反驳;未验证主张不得作为调整 severity/confidence 的依据。防御"一条幻觉主张在 3 轮内感染全部 reviewer"的级联风险(From Spark to Fire, 2026)。

推理策略多样性STRATEGY DIVERSITYNEW

每个 reviewer 模板在 frontmatter 声明 reasoning_strategy(checklist/inverse/transform/counterfactual/falsification),系统在 system prompt 中注入对应推理策略指引。引擎的 deterministic_panel 贪心选择确保面板内至少 2 种不同策略——打破"所有 reviewer 共享同一推理范式、共享同一盲区"(DMAD, ICLR 2025:不同推理方法 per agent >> 不同 persona per agent)。

自动辩论强度AUTO SKEPTICISMNEW

Phase 2 的质疑强度由 Phase 1 实测信号自动推断:发现 critical 或 reviewer 严重分歧(consensus < 0.5)→ 高质疑(0.9);全员一致且仅 minor → 低质疑(0.4)快速收敛;其余 → 中等(0.7)。零外部配置,用户无需调参。调节此参数可带来 ~15% 性能波动(Should we be going MAD?, 2024)。

三级行动决策3-TIER ACTIONNEW

Verdict 输出 green/yellow/red 三级,决定审查结果如何指导行动。GREEN 时 AI 可自行修复(置信 ≥ 0.9 且 ≤ minor 且全部有 suggestion);YELLOW 需人工确认方案;RED 必须人工介入。judge-manager 按级别分级汇报,人工介入时提供完整报告+校准结果+流程审计。阈值可通过 evaluate --recommend-threshold 基于历史数据用 Youden's J 校准。

第四条 NEW

行动决策全景

审查完成后,系统输出三级行动决策,决定"AI 能不能动""要不需要人确认""必须人工介入"。

● GREEN
AI 可自行修复
置信 ≥ 0.9 AND severity ≤ minor AND 全部 finding 有 suggestion
  • judge-manager 汇报 findings + 建议
  • "置信度足够,建议由 AI 直接修复"
  • 用户确认 → 原始产出 AI 按 suggestion 执行
  • 修复后可选: 再次审查(递归)
● YELLOW
需人工确认修复方案
置信 ≥ 0.8 但存在 major 问题,或部分 finding 缺 suggestion
  • judge-manager 汇报全部 findings(按 severity 排序)
  • 每条含 evidence + suggestion(空则标"需人工排查")
  • route 字段说明流程与门控理由
  • 用户审阅 → 决定方案 → AI 或人工执行
● RED
必须人工介入
置信 < 0.8 OR severity = critical OR 元审查发现 critical 校准问题
  • 明确说明"为什么需要人工"(action_reasoning)
  • 全部 findings + 元审查校准结果
  • 流程审计: route/consensus/stability/conformity
  • 完整产物: report.md + verdict.json + results/

什么情况修不了

场景原因为什么 AI 修不了
置信度不足 reviewer 严重分歧或元审查发现推理缺口 AI 自己都没搞清楚问题在哪
severity = critical 问题严重到可能需架构级调整 需人工判断: 改文档? 改设计? 改需求?
元审查 critical 原始审查本身有重大漏判 不能信任 AI 的 finding,需人工重审
finding 缺 suggestion 发现问题但给不出修复建议 人工需自行判断如何修复
结构性分歧 consensus < 0.5,reviewer 根本对立 不是修一个 finding 能解决的

修改的 AI 是谁

GREEN 区间下,judge-manager 向用户汇报并建议直接修复。用户确认后,由原始产出 AI 执行修复(写文档的那个 agent 最了解上下文)。judge-manager 本身不执行修复——它只输出 verdict + action 建议。这符合系统红线:judge-manager 禁止自行扮演 reviewer 或做流程决策。用户也可选择让另一个 AI 修或自己修,judge-manager 不强制。

人工介入时提供的信息

信息项内容用途
findings 列表 按 severity 排序,每条含 description/evidence/severity/confidence/suggestion 人工逐条审查和修复
action_reasoning 为什么需要人工(置信度数值 + 阈值对比) 快速理解介入原因
元审查结果 calibrated_confidence vs 原始 confidence 的差异;meta-reviewer 的 confidence_adjustment 判断原始审查是否可信
route 字段 实际走的流程(哨兵/standard/thorough) + 门控理由 审计流程决策是否合理
consensus / stability reviewer 间一致度 + 辩论前后立场稳定性 判断分歧程度
conformity_warnings 附和检测 + 溯源违规检测 判断 reviewer 是否被误导
产物路径 report.md(人类阅读) + verdict.json(机器消费) + results/(推理过程) + state.json(状态轨迹) 完整可追溯
第五条

边界与渊源

5.1

不做传统 code review。

代码风格、命名规范、设计模式、性能微优化不属本系统职责,由 SonarQube / ESLint / 人工处理。

5.2

可审查检视工具的产物。

外部代码检视报告本身是否可靠(覆盖度、误报漏报、定级合理性、建议可执行性)可作为输入被本系统复审。

5.3

不审查需求收集过程。

需求收集是原始输入采集,AI 无产出物,不产生幻觉。需求澄清/分解/优先级等过程活动的产出合入规格文档,由 spec-reviewer 统一覆盖(歧义消除、MECE、验收标准可测试性等维度)。

5.4

渊源。

受 Agent-as-a-Judge(ICML 2025)启发的重写:继承其多数投票聚合、置信度公式与 AUROC 校准评估;辩论编排、元审查、升级路由与状态机为全新构建。溯源标记借鉴 From Spark to Fire(2026);推理策略多样性借鉴 DMAD(ICLR 2025);自动辩论强度借鉴 Should we be going MAD?(2024)。MIT 许可。
