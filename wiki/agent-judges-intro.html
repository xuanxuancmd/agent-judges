所有 AI 产出，
都必须被对抗审查。

agent-judges 是一套 AI 产出审计系统:由确定性引擎驱动一组 互相挑战的 reviewer(评审者),横跨需求、规格、设计、测试计划等全部交付物, 产出可审计、可升级、可再次审查的裁决——而不是某个更强模型的单方面保证。

// 理念 PRINCIPLES

四条立场

01 / 对抗

对抗性来自结构，而非单兵。

不指望"一个更强的 judge"。独立评审、对抗辩论、盲评终判、裁决合成——四阶段固定流程逼 reviewer 互相挑战。reviewer 无自主性、不调工具、不决定流程:是合议庭,不是 agent team。

02 / 编排

流程归引擎，LLM 只做判断。

渐进门控、辩论推进、裁决合成、升级路由,全部由 prepare / resume 状态机确定性推进。任何 LLM——包括宿主——都无权编排流程。理由同上:单 agent 不可靠,所以更不能让单个 LLM 拿走编排权。

03 / 自省

审查者也是 AI，同样不可靠。

verdict(裁决)可作为输入,交由 ≥2 个异构 meta-reviewer 复审——查漏判、过判、置信度失准、共识假象;置信度经显式公式校准,而非简单覆盖。是否升级人工,只认校准后的值。

04 / 升级

判不动，就交人。

每条 finding 与整体裁决都携带量化置信度;低于阈值,自动标记 escalate_to_human。系统的目标不是替代人:高置信处自主,低置信处召回。

// 流程 PIPELINE

渐进门控 × 四阶段辩论

零参数调用时,系统不做先验复杂度分类:哨兵先行,用 Phase 1 的实测信号驱动两道纯规则门。流程强度由结果决定,而非入口处的预测;完整路径记录于 verdict 的 route 字段,可复盘。

  1. Step 1 哨兵先行 短文(< 8k token)派 1 名哨兵独立评审;长文直接 3 人面板
  3. Gate 1 · 纯规则 早停判定 哨兵未发现 major 且置信 ≥ 0.9 → 判定"简单",直接输出
  5. Step 2 面板扩张 哨兵 verdict 保留,不重复计算;补足至 3 人并行独立评审
  7. Gate 2 · 纯规则 续跑强度 发现 critical 或加权置信偏低 → thorough 续跑;否则 standard
  9. Final 终态 按选定强度完成四阶段辩论,产出 verdict 与报告
Phase 1

独立评审

  • N 名 reviewer 并行,互不可见
  • 耗时 ≈ 单次延迟,而非 N 倍
  • 超长输入自动截断保护
Phase 2 · 对抗

对抗辩论

  • 阅他人观点后逐条反驳
  • 1–3 轮,每轮前检查预算
  • ≥2 名 reviewer 方开启
Phase 3

盲评终判

  • 辩论后各自独立终判
  • 终判互不可见,防从众
  • 单 reviewer 快检自动跳过
Phase 4

裁决合成

  • severity 取最严(critical > major > minor > pass)
  • 置信度按 reviewer 权重加权
  • 产出 consensus / stability 评分
Meta Review元审查(thorough 档)

verdict 本身被 ≥2 个 meta-reviewer(不同模型、不同视角)再次审查:漏判、过判、置信度失准、推理缺口、共识假象、完整性。校准使用显式公式,升级判定只认校准值:

calibrated_confidence = confidence × ( 1 − meta_penalty )  // critical 0.5 · major 0.3 · minor 0.1

// 技术 CAPABILITIES

关键技术点

K1

异构 reviewer 面板

不同角色配不同模型(Claude + GPT-4o 等),避免同模型共享盲区;模型写在 reviewer 模板 frontmatter,省略即用宿主默认。

K2

元审查与显式校准

审查结果再被审查:≥2 个 meta-reviewer 异构复审,置信度按显式公式校准——而非"再跑一遍"式的简单覆盖。

K3

置信度驱动人工升级

校准置信低于阈值 → 自动标记 escalate_to_human;每条 finding 附证据引用与可执行建议,交人即可裁决。

K4

零代码扩展

reviewer 用 Markdown 模板定义(persona + checklist),SKILL.md 知识包注入领域 rubric;新增视角不改一行代码。

K5

宿主零配置

一条命令装入 Claude Code / OpenCode:judge-manager + 实体 reviewer Agent,模型、凭证、额度全部来自宿主已有配置。

K6

递归自审

verdict 序列化后可再次作为输入被审查(深度上限 2)——"审查者不可靠"的主张,对系统自身同样成立并被兑现。

// 边界 SCOPE & ORIGIN

不做什么

不做传统 code review:代码风格、命名规范、设计模式、性能微优化——交给 SonarQube / ESLint / 人工。但这些工具的产物(检视报告本身是否可靠),可以作为本系统的输入被审查。

渊源

受 Agent-as-a-Judge(ICML 2025)启发的重写:继承其多数投票聚合、置信度公式与 AUROC 校准评估;辩论编排、元审查、升级路由、状态机为全新构建。审查对象是产出物,不是执行轨迹。
